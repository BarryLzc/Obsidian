在 **可重复读 (RR)** 级别下，MVCC 只能解决“快照读”（普通查询）的幻读。但如果你执行的是“当前读”（修改数据的操作），就需要靠锁机制来镇场子了。

---

## 核心机制：Next-Key Locks

Next-Key Lock 实际上是 **行锁 (Record Lock)** 和 **间隙锁 (Gap Lock)** 的组合。

### 1. 行锁 (Record Lock)

最基础的锁，锁住具体的某一行索引记录。防止其他事务对这一行进行修改或删除。

### 2. 间隙锁 (Gap Lock)

**这是解决幻读的关键。** 它锁住的是索引记录之间的“空隙”，而不是记录本身。

- **目的**：防止其他事务在这个间隙内**插入**新数据。
    
- **例子**：如果表中只有 ID 为 10 和 20 的记录，间隙锁可以锁住 $(10, 20)$ 这个区间。这时，你想插入 ID 为 15 的记录会被阻塞。
    

### 3. Next-Key Lock (临键锁)

它是行锁和间隙锁的结合，锁住的是一个**左开右闭**的区间。

- **公式**：Next-Key Lock = $(Previous\_Key, Current\_Key]$。
    
- 比如索引序列为 10, 20, 30，如果你对 20 加了 Next-Key Lock，那么锁定的范围就是 $(10, 20]$。
    

---

## 它是如何解决幻读的？

假设有一张表，ID 只有 5 和 10。

1. **事务 A 执行当前读**：`SELECT * FROM table WHERE id > 7 FOR UPDATE;`
    
2. **加锁过程**：
    
    - InnoDB 会找到第一个大于 7 的记录，即 ID=10。
        
    - 给 10 加一个 Next-Key Lock，锁定范围是 $(5, 10]$。
        
    - 为了防止在 10 后面插入数据，还会给 $(10, +\infty)$ 加一个间隙锁。
        
3. **结果**：此时事务 B 想要执行 `INSERT INTO table (id) VALUES (8);` 或者 `INSERT INTO table (id) VALUES (12);` 都会被阻塞挂起。
    

**结论**：因为间隙被锁死了，新数据插不进来，事务 A 第二次查询时结果集依然是一样的，从而完美解决了幻读。

---

## 避坑指南：RR 级别依然可能出现幻读的情况

虽然有了 MVCC 和 Next-Key Locks，但在一种特殊操作下仍会产生“幻象”：[[RR级别下的幻读]]

- **操作步骤**：
    
    1. 事务 A 开始，SELECT 一条不存在的记录（快照读，看到 0 条）。
        
    2. 事务 B 插入该记录并提交。
        
    3. 事务 A 执行 UPDATE 这条**原本不存在**的记录（UPDATE 是当前读，会触发 Next-Key Lock，并更新该行的隐藏版本号为事务 A 的 ID）。
        
    4. 事务 A 再次 SELECT，发现记录居然出现了！
        

**一句话总结**：要完全杜绝幻读，建议在开启事务后，第一步就通过 `FOR UPDATE` 进行“当前读”加锁。
```
BEGIN;
-- 1. 查询时直接锁死这行，别人无法同时查询这行进行修改
SELECT stock FROM products WHERE id = 1 FOR UPDATE; 
-- 2. 执行更新
UPDATE products SET stock = stock - 1 WHERE id = 1;
COMMIT; -- 提交后，锁才释放
```
