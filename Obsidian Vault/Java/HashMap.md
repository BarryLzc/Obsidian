## 1. 为什么要引入[[红黑树]]？

在 Java 7 之前，HashMap 只使用链表处理哈希冲突。

- **痛点**：如果大量数据的 `hashCode` 相同，链表会变得非常长，查询时间复杂度会从 $O(1)$ 退化为 $O(n)$。
    
- **优化**：Java 8 引入红黑树，将极端情况下的查询复杂度降低到 $O(\log n)$。
    
- **思考**：为什么[[InnoDB]]不实用红黑树，用B+树呢？因为无法利用磁盘预读的特性，数据库每次从磁盘拿数据，起步就是16KB的，而红黑树每个节点只有 2 个分支（度为 2），这导致了它在处理海量数据时，**需要的IO太多了**。而B+数是一个巨大的公文包，可以一次处理很多数据。
---

## 2. 红黑树的 5 大特性

红黑树是一种**自平衡二叉查找树**，它必须满足以下规则：

1. **节点颜色**：每个节点要么是红色，要么是黑色。
    
2. **根节点**：根节点永远是**黑色**。
    
3. **叶子节点**：所有的叶子节点（NIL 节点）都是黑色。
    
4. **红色限制**：红色节点不能相邻（即红色节点的父节点和子节点必须是黑色）。
    
5. **黑高一致**：从任一节点到其每个叶子的所有简单路径都包含相同数量的黑色节点。

## 3. HashMap 中的转换阈值

Java 8 并不是一开始就使用红黑树，而是根据特定条件触发转换：

- **链表转树（Treeify）**：当桶位（Bucket）中的链表长度 **> 8**，且数组总容量 **≥ 64** 时，链表转为红黑树。
    
- **树转链表（Untreeify）**：当扩容或删除节点导致树中的节点数 **≤ 6** 时，红黑树退化回链表。
    

> **为什么是 8？** 根据泊松分布，在哈希函数随机性良好的情况下，链表长度达到 8 的概率极低（约千万分之六）。选择 8 是一种在空间和时间上的平衡。

---

## 4. 核心修复操作

当插入或删除节点破坏了红黑树的特性时，Java 会通过以下三种方式进行“自我修复”：

|**操作**|**说明**|
|---|---|
|**变色 (Color Flip)**|改变节点的颜色（红变黑，黑变红）。|
|**左旋 (Left Rotate)**|将某个节点向左下方移动，其右子节点变为父节点。|
|**右旋 (Right Rotate)**|将某个节点向右下方移动，其左子节点变为父节点。|

---

## 5. Java 8 源码中的关键类：TreeNode

在 `java.util.HashMap` 中，红黑树的实现由内部类 `TreeNode` 承担。它继承自 `LinkedHashMap.Entry`（进而继承自 `Node`）。

**关键属性：**

- `parent`: 指向父节点。
    
- `left`: 左子节点。
    
- `right`: 右子节点。
    
- `prev`: 前驱节点（用于在转换回链表时保持顺序）。
    
- `red`: 布尔值，记录颜色。
