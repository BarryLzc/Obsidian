## 1. 旁路缓存模式 (Cache Aside Pattern)

这是最常用的基础方案，分为两种操作顺序：

### A. 先更新数据库，再删除缓存（推荐）

这是目前的**行业标准做法**。

- **逻辑：** 数据更新时，先写数据库，成功后直接删除缓存。下一次读取时，缓存缺失再从库中加载。
    
- **优点：** 出现不一致的概率极低。
    
- **风险：** 在极端高并发下，如果写操作删缓存失败，或者在缓存失效瞬间有读请求并发，可能导致短暂旧数据。
    

### B. 先删除缓存，再更新数据库

- **逻辑：** 先把缓存删掉，再去改数据库。
    
- **缺点：** **严重不推荐**。在高并发下，线程A删了缓存还没改完库，线程B进来发现没缓存，直接把旧库数据读出来写回缓存，导致缓存永远是脏数据。
    

---

## 2. 延时双删策略 (Delayed Double Delete)

为了解决“先删缓存”模式下的并发问题，演变出了双删：

1. 删除缓存。
    
2. 更新数据库。
    
3. **睡眠一段时间**（如 500ms）。
    
4. 再次删除缓存。
    

> **核心逻辑：** 第二次删除是为了确保在更新数据库期间，由于并发读请求产生的“脏缓存”被清理掉。

---

## 3. 基于 Binlog 的异步更新（高阶方案）

这种方案将缓存更新与业务逻辑**解耦**，是大型互联网公司（如阿里、美团）常用的方案。

- **流程：** 业务只管更新数据库，不手动操作缓存。
    
- **实现：** 利用 **Canal** 等中间件伪装成 MySQL 的 Slave，监听 **Binlog** 日志。一旦数据库有变动，Canal 抓取到消息并投递到 MQ（消息队列），由消费者异步更新/删除缓存。
    
- **优点：** * 业务代码干净。
    
    - MQ 保证了任务的可靠性（有重试机制）。
        

---

## 4. 读写穿透 (Read/Write Through)

这种方案将缓存视为“唯一数据源”，由缓存服务自己去同步 DB。

- **Write Through：** 写请求发给 Cache，Cache 同步写入 DB，两者都成功才返回。
    
- **Read Through：** 读请求发现 Cache 缺失，由 Cache 代理去拉取 DB 并回填。
    
- **缺点：** 实现复杂，通常需要专门的缓存中间件支持（如 Guava Cache 或某些分布式缓存框架）。
 ---

## 5. 异步回写 Write-Behind (Write-Back)，秒杀场景

在秒杀这种高并发场景下，数据库（MySQL）的 IOPS 无法支撑每秒数万次的减库存操作，因此我们必须把数据的主战场转移到缓存（Redis）中。

### 核心流程

1. **用户下单：** 直接在 Redis 中进行原子扣减库存（如使用 Lua 脚本）。
    
2. **立即返回：** 只要 Redis 扣减成功，直接告诉用户“抢购成功”。
    
3. **异步同步：** * **方式 A（Write-Behind）：** 扣减成功后，发送一条消息到 MQ，由消费者慢慢写回数据库。
    
    - **方式 B（定时批量）：** 开启一个定时任务（Job），每隔一段时间（如 1 秒）将 Redis 中的库存增量批量同步回数据库。
        

---

### 为什么秒杀场景要用它？

秒杀场景的特点是 **“极高并发、写强于读、允许极短时间的不一致”**。

- **性能极高：** 所有的写操作都在内存中完成，响应速度在毫秒级。
    
- **数据库保护：** 数据库不再承受瞬时的压力峰值，而是接收平稳的、经过合并后的异步请求。
    
- **批量合并：** 定时任务可以将 1000 次扣减操作合并成一条 `UPDATE inventory SET count = count - 1000` 语句，极大地减轻了数据库的事务压力。
    

---

### 存在的风险与应对方案

这种方案虽然快，但它是**可靠性换取性能**的典型，存在以下隐患：

|**风险点**|**表现**|**应对措施**|
|---|---|---|
|**数据丢失**|如果 Redis 挂了且持久化没做，或者异步任务没跑完，数据库里的库存就是错的。|开启 Redis AOF 强持久化；利用 MQ 的持久化机制保证消息不丢失。|
|**超卖问题**|如果逻辑处理不当，异步回写时发现数据库库存不够。|**必须以 Redis 为准**。在 Redis 端进行预校验，数据库层面只做最终结果的落盘。|
|**一致性延迟**|数据库里的数据在秒杀期间是“虚假”的旧数据。|后台管理系统（如发货系统）必须读取数据库，但由于秒杀商品发货有延迟，这种分钟级的最终一致性通常是业务可接受的。|

---

### Write-Behind总结

秒杀场景下的“异步批量同步”属于 **Write-Behind** 模式的变种。它与常见的 **Cache Aside**（先写库后删缓存）完全相反：

- **Cache Aside**：以数据库为准，适合大多数对数据准确性要求高的业务。
    
- **Write-Behind**：以缓存为准，适合极致并发、对实时一致性要求稍低的场景。
---

## 6. 方案对比总结

|**方案**|**一致性程度**|**复杂度**|**适用场景**|
|---|---|---|---|
|**先写库，再删缓存**|较高（最终一致）|低|大多数通用业务|
|**延时双删**|中|中|解决先删缓存带来的并发问题|
|**Binlog 异步同步**|高|高|复杂系统、对业务代码解耦要求高|
|**分布式锁**|强一致|极高|对数据准确性要求极高的金融场景（性能损耗大）|
