# RFC 9421 的局限与能力边界

|**RFC 9421 能做的事**|**RFC 9421 做不到的事**|
|---|---|
|**验证防篡改：** 确保请求方法、URI、Header 或结合 Digest 的 Body 没被中途修改。|**保密/防偷窥：** 明文传输的敏感数据（如用户个人信息、卡号）依然是明文。|
|**验证身份（防伪造）：** 证明请求确实来自拥有对应私钥的发送方。|**隐藏元数据：** HTTP Header 和 Component 名称依然暴露在网络中。|
|**防重放攻击：** 通过 `created`、`expires` 和 `nonce` 参数避免请求被重复利用。|**替代传输层加密：** 无法阻止网络抓包者读取 HTTP 报文内容。|
# 如何在实际架构中解决“既要验证，又要加密”？
在实际生产（如 UCP 协议或高安全 B2B API）中，RFC 9421 从不单独工作，而是与传输层或应用层加密配合：

## 1. 结合 TLS/HTTPS（最常见）

- **TLS 负责保密性（Encryption）：** 确保数据在网络传输管道中被加密，中间人抓包只能看到乱码。
    
- **RFC 9421 负责应用层与端到端完整性（End-to-End Authentication）：** 解决“经过了多跳 API 网关/反向代理后，网关解密了 TLS，但后端仍需验证原始客户端身份与内容未被网关非法篡改”的问题。

## 2. 结合应用层加密（Payload Encryption）

如果在去中心化或零信任网络中，数据需要经过完全不受信任的中间节点转发：

- 业务方会先用接收方的公钥对敏感 Body 进行应用层加密（如 **JWE - JSON Web Encryption** 或 **HPKE - RFC 9180**）。
    
- 随后使用 **RFC 9421** 对加密后的 Body 摘要（`Content-Digest`）及 HTTP 元数据进行签名。

# 总结

可以将 RFC 9421 想象成**公文上的红章/合同签名**： 签名能证明合同是某人签署的、且没有被偷偷撕页改字（验证与抗抵赖），但它本身是一张公开的纸，任何人都能拿起来读（无加密）。要防止别人读，必须把它装进加密信封（TLS 或 JWE）里。
