# Paxos算法
## 算法概览

1. 设计目的：解决拜占庭将军问题，解决分布式系统中的共识（一致性）问题
2. 算法原理：通过Propose、Accept和Learner三个阶段保证决策的一致：
	- Proposer：提议者是启动共识过程的节点，它提出一个值，请求其他节点对这个值进行投票，提出值的行为称为发起“提案"（Proposal），提案包含提案编号 (Proposal ID) 和提议的值 (Value)。注意的是，Paxos 算法是一个典型的为“操作转移”模型设计的算法，为简化表述，本文把提案类比成“变量赋值”操作，但你应该理解它是“操作日志”相似的概念，后面介绍的 Raft 算法中，直接就把“提案”称做“日志”了。
	- Acceptor：接受或拒绝提议者发起的提案，如果一个提案被超过半数的决策者接受，意味着提案被“批准”（accepted）。提案一旦被批准，意味着在所有节点中达到共识，便不可改变、永久生效。
	- Learner：记录者不发起提案，也不参与决策提案，它们学习、记录被批准的提案。
3. 问题：
	- 算法论证过于负责，不好解释
	- 多个 Proposer 并行时容易造成提案冲突（不断重新投票，**活锁问题**），所以真实使用paxos算法基本都是使用multi-paxos来实现proposal（日志）复制
# Raft算法
## 算法概览
1. 设计目的：主要也是为了解决分布式系统中的共识（一致性）问题，其次是因为Paxos算法原理和论证过于复杂，这也是Raft算法后来居上的原因。
2. 算法原理：通过设置领导者（Leader）、追随者（Follower）和候选人（Candidate）简化一致性问题，由Leader发起决策，Follower和Candidate执行决策，其算法的核心是Leader选举算法。
3. 选举人算法原理：假设当前某个节点（我们称为 `A`）发起选举，流程如下：

**进入 Candidate 状态**
    
    - 节点 `A` 增加自己的任期号 `currentTerm += 1`
        
    - 给自己投一票（`votedFor = self`）
        
    - 向集群中所有节点发送 `RequestVote` RPC 请求
        
**RequestVote RPC 内容**  
    包含以下信息：
    
    - `term`：当前候选人的任期号
        
    - `candidateId`：候选人ID
        
    - `lastLogIndex`、`lastLogTerm`：候选人最后一条日志的位置和任期号
        
**Follower 处理投票请求的规则**  
    当其他节点（Follower）收到 `RequestVote` 请求时，会进行如下判断：

| 判断条件                                    | 说明   |
| --------------------------------------- | ---- |
| 请求任期号 `term` < 自己当前任期                   | 拒绝投票 |
| 当前任期内已经给别人投过票且不是这个候选人                   | 拒绝投票 |
| 候选人日志不够新（基于 lastLogTerm / lastLogIndex） | 拒绝投票 |
| 否则                                      | 拒绝投票 |

    
**候选人统计投票**
    
    - 若收到超过半数节点的投票包括自己），则成为新的 Leader；
        
    - 若收到了其他节点的心跳（说明有别的 Leader 已经当选），则重新变回 Follower；
        
    - 若在超时时间内未当选（票数不足或平票），重新开始新一轮选举。

# Paxos vs Raft 对比总结
| 对比项       | **Paxos**                     | **Raft**                        |
| --------- | ----------------------------- | ------------------------------- |
| **设计目标**  | 保证一致性（理论正确性）                  | 保证一致性 + 易于理解和实现                 |
| **领导机制**  | 没有固定 Leader（可并行提案）            | 明确的单 Leader                     |
| **核心阶段**  | Prepare + Accept              | 选举 + 日志复制                       |
| **节点角色**  | Proposer / Acceptor / Learner | Leader / Follower / Candidate   |
| **实现复杂度** | 高（概念抽象，难以编码）                  | 低（逻辑清晰，工程常用）                    |
| **性能**    | Multi-Paxos 接近 Raft           | Raft 稳定性能更好，冲突少                 |
| **可理解性**  | 理论性强，晦涩难懂                     | 模块清晰，易讲解易实现                     |
| **应用场景**  | 学术研究 / Google Chubby          | Etcd, Consul, TiKV, CockroachDB |
