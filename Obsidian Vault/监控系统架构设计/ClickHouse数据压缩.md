1.  ZSTD all the way：无需编解码器的 ZSTD 在压缩方面通常优于其他选项，或者至少具有竞争力：尤其是在浮点方面。因此，这是我们在 ClickHouse Cloud 中的默认压缩方式。
2. Delta for integer sequences：每当序列为单调序列或连续值中存在较小增量时，基于 Delta 的编解码器都能很好地工作。更具体地说，如果导数产生的值较小，Delta 编解码器就能很好地工作。如果不是，DoubleDelta 编解码器值得一试（如果 Delta 的一阶导数已经很小，则 DoubleDelta 编解码器的效果通常不大）。对于单调增量均匀的序列，压缩效果会更好——看看日期字段的显著节省就知道了。
	- 非常适合连续变化的数据（时间序列、排序整数等），如果数据变化剧烈（随机跳动），Delta 效果反而变差。
	- 解压时只需逐步还原，不能直接按值查找，适合顺序读取场景。
3. Maybe Gorilla and T64 for unknown patterns：如果数据存在未知模式，不妨尝试 Gorilla 和 T64。Gorilla 主要针对数值变化较小的浮点数据而设计。它专门计算当前值和先前值之间的异或，并以紧凑的二进制形式写入：当相邻值相同时，效果最佳。更多信息，请参阅《在 Gorilla 中压缩值：一个快速、可扩展的内存时间序列数据库》。它也可用于整数。然而，在我们的测试中，即使与这些编解码器结合使用，普通的 ZSTD 性能也优于它们。和其它编码器做比较：
	- Gorilla：适合浮点数时间序列。
	- Delta：适合线性变化。例如，原始数据为：100、101、102、104、107，做Delta编码后：100、+1、+1、+2、+3。再经过如 ZSTD 的压缩器处理 `[100, 1, 1, 2, 3]`，压缩率会比直接压原始值高很多。
	- DoubleDelta：适合加速度趋势（即二阶变化稳定，比如增长速度恒定）
	- T64：矩阵去重，适合重复值多、低基数数据。例如，假设一列中有 100万个记录，但只有 10 个不同的值重复出现：100, 100, 100, 90, 90, 100, 80, 80, ...。传统压缩器只能按字节流压缩，但 `T64` 会建立一个小的值表，比如：Table:
				0 -> 100
				1 -> 90
				2 -> 80
				...

				Encoded: 0, 0, 0, 1, 1, 0, 2, 2, ...
4. T64 for sparse or small ranges：上文已证明，T64 算法在处理稀疏数据或块内范围较小时非常有效。请避免对随机数使用 T64 算法。
5. Gorilla possibly for floating point and gauge data ：其他帖子强调了 Gorilla 对浮点数据的有效性，特别是那些表示仪表读数（即随机尖峰）的数据。这与算法属性相符，尽管我们上面的数据集中没有字段可供验证。我们上面的测试表明，至少在 Float32 上，ZSTD 提供了最佳的浮点压缩率。
6. Delta improves ZSTD ：ZSTD 是一种处理增量数据的有效编解码器——相反，增量编码可以改进 ZSTD 的压缩率。高于 3 级的压缩率很少能带来显著的提升，但我们建议进行测试。在 ZSTD 存在的情况下，其他编解码器很少能带来进一步的改进，正如我们上面的结果所示。我们曾看到报告称，LZ4 在 DoubleDelta 编码数据上的压缩率优于人工数据集上的 ZSTD，但我们尚未在真实数据集上找到这方面的证据。
7. LZ4 over ZSTD if possible：如果 LZ4 和 ZSTD 的压缩率相当，则建议选择前者，因为它解压速度更快，CPU 占用更低。不过，在大多数情况下，ZSTD 的性能会显著优于 LZ4。有些编解码器与 LZ4 结合使用时，压缩率可能更快，但压缩效果与不带编解码器的 ZSTD 相当。不过，具体情况取决于具体数据，需要测试。
