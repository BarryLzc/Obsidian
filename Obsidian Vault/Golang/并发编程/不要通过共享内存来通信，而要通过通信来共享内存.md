这是 Go 语言中一句经典的设计哲学：**"Do not communicate by sharing memory; instead, share memory by communicating."** 要理解这句话，需要对比两种并发编程模型。
### 传统方式：通过共享内存来通信

多个线程访问同一块内存（比如一个共享变量），用锁（Mutex）来协调：

go

```go
var count int
var mu sync.Mutex

// 多个 goroutine 同时操作
mu.Lock()
count++
mu.Unlock()
```

这种方式的问题在于：随着共享状态和锁的增多，代码会变得极其脆弱——忘记加锁导致数据竞争，加锁顺序不对导致死锁，锁粒度不当导致性能瓶颈。程序员的心智负担很重，因为你需要时刻思考"谁在什么时候可能访问这块内存"。

### Go 的方式：通过通信来共享内存

用 channel 把数据的**所有权**从一个 goroutine 传递给另一个：

go

```go
ch := make(chan int)

go func() {
    result := doWork()
    ch <- result // 把结果"交出去"
}()

val := <-ch // 接收方获得数据的所有权
```

数据通过 channel 发送出去之后，发送方就不再持有它了。任意时刻只有一个 goroutine 拥有这份数据，根本不需要锁。

### 为什么 Go 更推崇这种方式

**本质区别是思维模型的不同：**

共享内存的思路是"多个人同时看同一块黑板，靠规则来避免冲突"。通信的思路是"我把纸条递给你，递出去之后纸条就是你的了"。后者天然避免了并发冲突，因为数据在任何时刻只有一个主人。

具体好处包括：数据流向在代码中是显式的，你能直接看到谁发、谁收；goroutine 之间的协作关系通过 channel 的拓扑结构自然表达出来，比如 pipeline、fan-out/fan-in 模式；不需要操心锁的获取释放顺序，大幅降低了出错概率。

**一句话总结：** 锁保护的是数据，channel 传递的是所有权。把"谁能访问数据"这个问题，从运行时的锁竞争变成了编译期可见的通信结构，程序就更容易写对、更容易理解。

当然 Go 也提供了 `sync.Mutex`，在某些场景（比如简单的引用计数、缓存）下共享内存加锁反而更直接。Go 的建议不是"禁止用锁"，而是"默认先想 channel，锁是备选"。
